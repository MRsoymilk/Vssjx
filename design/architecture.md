[返回设计索引](README.md) · [协议方案](protocol.md) · [路线图](roadmap.md)

性质：**目标架构与技术约束，部分已实现**。基础设计于 2026-10-15，状态说明于 2026-10-19 整理。账号、世界、PVE、队伍和社交已接入，但下文的统一角色邮箱、跨模块状态机与恢复策略不能直接当作当前代码说明。实际接口以专题、源码及 `shared/` 为准，验收见 [联机测试计划](../tests/online_test_plan.md)。

## 1. 当前代码与客户端业务边界

当前提供本地与联机模式：本地由客户端保存角色和结算，线上由 Rust 服务与 PostgreSQL 校验并保存资产。下表说明离线模块与目标适配职责，不表示线上仍由客户端掌握权威状态。

| 客户端路径 | 本地模式职责 | 线上职责与适配目标 |
|---|---|---|
| `client/scripts/game_state.gd` | 属性、背包、升级、任务、本地存档 | 权威业务迁到服务端；客户端只保留显示快照与离线适配 |
| `client/scripts/battle.gd` | 回合计算、随机数、奖励落盘 | 线上由服务端计算与保存，客户端播放事件 |
| `client/scripts/world.gd` | 地图、阻挡、寻路、巡逻、交互 | 服务端校验与同步；客户端输入、预测和渲染 |
| `client/scripts/main.gd` | 页面以及直接修改角色的业务入口 | 页面经GameService调用，不再直接写线上资产 |
| `client/scripts/inventory.gd` | 背包展示、本地资源操作 | 展示快照；服务器确认后更新 |

### 1.1 业务适配

```text
页面、HUD、人物/背包/战斗界面
              ↓ GameService（类型化业务请求与快照信号）
      OfflineAdapter                 OnlineAdapter
      原本地规则与独立存档              NetworkClient → HTTPS/WSS
```

`GameService`是统一接口，不要求GDScript与Rust共用源码。线上不能继续调用本地`battle.commit()`、`Game.add_rewards()`、`Game.restore()`或`Game.save_game()`改变线上资产。界面可乐观显示移动，但购买、扣款、用药和发奖不得先按本地规则确认成功。D05已确认保留离线/在线双入口，存档完全隔离，不自动导入本地资产。

必须迁移或明确留在本地的入口如下，不能只改`game_state.gd`后宣布完成：

| 原入口 | 服务端规则/契约 |
|---|---|
| `main.gd::_world_interaction` | 挑战前置任务、地图归属、传送资格、出生位置 |
| `main.gd::_npc` | 接任务、领奖、NPC恢复及交互距离；领取奖励与恢复一并提交 |
| `main.gd::_rest` | 调息扣5铜钱与恢复原子完成；金额由配置决定 |
| `main.gd::_school`、`_return_from_attributes` | 门派身份、签名的类型、长度、权限和保存 |
| `inventory.gd::use_item/equip_item/buy_potion/confirm_discard` | 库存实例/堆叠、装备状态、容量、消耗和金币 |
| `inventory.gd::sort_items` | 首版作为本地显示排序，不改变物品身份；未来若改变服务器槽位需新增契约 |
| `battle.gd::commit` | 消耗、胜败、奖励、任务进度、升级恢复、战败回城 |
| 自动保存、退出和重登 | 本地存档仅供离线；在线通过服务器位置保存与权威快照恢复 |

物品定义ID不等于库存堆叠/物品实例ID，丢弃不能只凭显示格子索引或`potion`类型删除。保持现有60格、每堆最多99个、未装备剑占格等规则；装备/卸下检查同一权威库存，禁止客户端仅按本地显示格数判断。

### 1.2 网络与界面生命周期

`NetworkClient`独立于地图节点、弹窗和战斗页面，切页面不销毁连接、不停止心跳或恢复流程。Godot的`WebSocketPeer`需要持续`poll()`，关闭握手期间也要继续处理，见[官方接口说明](https://docs.godotengine.org/en/stable/classes/class_websocketpeer.html)。

先把网络字节解析成有边界的数据对象，再在主线程按版本更新显示快照；每帧处理有时间/数量预算，同时监测总积压和最大延迟。不能让无限解析循环拖住画面，也不能无限缓存。打开个人页面只影响本人输入；私人怪物暂停按D06确认的服务端规则执行，不暂停整个共享世界。

## 3. 技术栈与拓扑

| 部分 | 方案 |
|---|---|
| 客户端 | Godot、GDScript |
| 服务端 | Rust稳定工具链；实施时锁定版本和依赖 |
| 运行时/网络 | Tokio、Axum、HTTPS/WSS |
| 协议/配置 | Serde、UTF-8 JSON、显式协议与配置版本 |
| 数据库 | PostgreSQL、SQLx、版本化迁移 |
| 可观测性 | tracing及指标；M1接入基本队列、事务和连接观测 |
| 初期部署 | Docker Compose、TLS反向代理、单游戏写进程与私网数据库 |

```text
Godot → TLS入口 → Rust进程
                   ├── 连接/认证注册表
                   ├── CharacterActor（每个活动角色一个）
                   ├── MapActor（每个地图实例一个）
                   ├── 公共聊天
                   └── PostgreSQL连接池
```

初期不引入Redis、消息队列、Kubernetes和多机分片。部署约束为同一世界仅一个游戏写进程；数据库约束是最后防线，不代表已具备多进程角色所有权协调。增加多进程或滚动双写前，必须另行设计所有权租约、隔离令牌、消息路由及失效恢复。

## 4. 状态所有者与执行模型

| 状态 | 唯一协调者/权威来源 | 可见范围 |
|---|---|---|
| 地图实体、连续位置、路线、可见集合 | MapActor | 同实例各自可见集合 |
| 账号、会话、撤销状态、角色归属 | 认证与会话模块/数据库 | 本人和受控管理接口 |
| 属性、货币、库存、装备、任务 | CharacterActor/数据库 | 本人 |
| 个人怪物是否可挑战/已击败 | CharacterActor/持久化个人遭遇记录 | 本人 |
| 个人怪物当前巡逻位置 | MapActor按角色隔离维护；资格由CharacterActor校验 | 本人 |
| 战斗状态、随机推进、结算 | CharacterActor调用纯战斗规则/数据库 | 本人；随机状态不下发 |
| 聊天消息、发言资格 | 聊天模块、认证/管理状态 | 已认证公共频道订阅者 |
| 动画、相机、局部预测、界面排序 | 客户端 | 本地表现 |

### 4.1 角色执行器

连接只收发消息，不拥有业务状态。`CharacterActor`在注册表中唯一，生命周期不随WSS断开结束；重连绑定原执行器。所有库存/战斗/任务写入，包括管理修正和后台超时结算，都走相同串行协调路径。

一个角色同时最多一个在途业务写事务；后续冲突命令进入有界队列或明确拒绝。异步等待数据库只阻塞这个角色的业务推进，不能阻塞地图循环或所有玩家。完成消息带`operation_id`、业务修订和所有者代次，执行器先落实已提交业务，再向当前连接投递。尚未受理的新输入必须校验当前连接代次。

断开旧连接不取消已经受理的业务。只允许抛弃旧连接的投递，不允许抛弃已提交事务的业务结果。事务提交结果未知时进入`RECOVERING`：查回执、等待原事务确定结束并重载角色；不发成功、不发确定失败、不启动冲突业务。单次查询没有回执不足以证明仍在运行的事务已经回滚。

| 标识 | 含义 |
|---|---|
| `connection_epoch` | 连接接管后递增；拒绝旧连接输入/投递，不用来回滚数据库 |
| `owner_epoch` | 角色执行器所有权代次；受控重建时在数据库中更新，旧所有者写入要被条件检查拦截 |
| `world_epoch` | 角色世界归属/可移动阶段变更代次；切图、进出战斗等关键转换递增并持久化 |
| `state_revision` | 一次角色业务提交的整体修订，用于一致快照与跨领域结果分组，不作为所有命令的共同前置条件 |
| 各领域revision | 角色属性/货币、库存、任务、战斗各自修订；普通位置不推进这些业务版本 |

替换角色执行器前，必须等待旧执行器写入结果可确定，或通过数据库所有权行锁/条件写入隔离旧所有者，再从提交后的状态恢复。仅提高内存代次或关闭旧任务不能消除在途数据库写入。所有权取得与业务写入统一锁定角色行，锁顺序为角色→战斗/任务→库存/账本，减少相反锁序。

### 4.2 玩法状态与连接状态分离

数据库保存稳定业务事实：`WORLD`或`IN_BATTLE`、地图归属、位置锚点、`active_battle_id`及版本。`ENTERING_BATTLE`、`TRANSFERRING`、`SETTLING`是执行器的协调阶段，不把它们当作半份已成功业务暴露。连接另有连接中、认证、同步、就绪、断开状态。

| 操作 | 准备阶段 | 原子提交 | 提交后/失败恢复 |
|---|---|---|---|
| 开始战斗 | MapActor停在合法格中心并返回交互证明，冻结本人；执行器校验任务和个人遭遇 | 创建战斗、预约个人遭遇、固定属性/规则、保存位置锚点、更新活动状态及回执 | 成功显示战斗标记；明确回滚才解除预约；结果未知保持恢复中 |
| 切图 | 冻结本人；校验传送资格与目标实例可接纳性，取得目标预留 | 地图/位置/world_epoch与回执一起提交 | 原图移除和目标图加入均幂等；通知失败按数据库重建，不能随意写回旧地图 |
| 最终战斗回合 | 计算最终行动及胜败；执行器进入结算阶段 | 战斗结束、资源、奖励、任务、遭遇状态、回城/留场位置、world_epoch与回执 | 地图表现按提交结果更新；推送丢失通过快照/回执恢复 |
| 在线业务恢复 | 封锁本人冲突输入、查清未知事务 | 必要的恢复/超时结算仍走幂等事务 | 重建地图归属后再允许操作，其他玩家继续运行 |

地图准备消息携带`transition_id`、`owner_epoch`、`world_epoch`和合法位置/目标证明；重复消息返回相同阶段结果。地图只确认“已冻结/已预留”，不等待执行器数据库事务，避免双方循环等待。证明有时效，超时后尚未开始的提交必须拒绝；数据库结果未知时不能由地图定时器擅自解冻本人。

提交后跨模块投递可以重试。先靠持久化状态、回执和受控对账修复，不为单进程引入独立消息中间件；若后续加入不可从状态恢复的外部副作用，另设同事务outbox。进程崩溃后不恢复半个内存准备阶段，而是根据数据库的稳定业务事实重建。

## 5. 地图、移动、个人目标与配置

地图采用四向格子路线，服务端持有阻挡、传送点、出生点、任务和怪物配置。权威数据导出必须包含`world.gd::_build_map()`地形以及`_add_scenery()`新增的树木阻挡，不能只导出地形。配置使用稳定ID、schema版本、内容摘要及规则版本；导出客户端可公开子集，不下发服务端随机状态和认证信息。

服务端和客户端加载同一份导出地图，不用“相同seed”各自生成权威阻挡。启动检查引用完整、出生点/传送落点可达、配置兼容。原有两张地图与后续显式接入的 AI 扩展分开维护，规则见 [AI 世界](ai-world.md)。

移动以地图任务的单调时钟为准，不采用客户端时间差。连续位置由已到达格、下一格、进度和路线版本共同推导。普通停止完成正在走的一格后停下；反作弊校正或关键转换使用服务器指定的合法格中心。客户端不能以反复停止、改目标、重发或断线累积额外位移。预测按确认输入回放，远端插值；步伐仍按实际显示位移推进。

按已确认D06，玩家互不阻挡，战斗时原地显示“战斗中”；个人页面暂停本人输入与个人怪物，但网络和其他玩家继续更新。私人暂停须服务端确认并有可配置的次数/时长保护，不赋予停止整个共享地图的权限。个人怪物存在性和击败记录归角色业务，巡逻仅发给本人。点击怪物发送目标身份/交互意图而不是伤害或位置真值；服务器根据当前合法位置和目标当前状态确认距离。若沿用点击后停下等待，需要服务器先确认有限时预约，失效后重新验证，不能信任客户端无限冻结目标。

目标模型中，一个个人遭遇使用`(character_id, encounter_id, spawn_generation)`作为身份。挑战期间是`RESERVED`，胜利时同事务标为`CONSUMED`；失败或逃跑释放预约但保留消耗。换 operation_id、battle_id 或重连不能绕过已结算约束。当前已接入角色级冷却与刷新，任务历史和冷却分离，见 [联机刷新](../tests/online_respawn.md)；本段不表示当前没有刷新。

## 6. 战斗规则、节奏与恢复

纯战斗函数输入为不可变规则快照、当前状态、合法指令和注入随机源，输出下一状态及有序事件，不直接操作网络或数据库。保留现有三职业、技能耗灵力9、用药恢复45、待机回灵5、防御/反震、30回合上限，以及无效/查看不推进回合的规则；数值最终从版本化配置读取。

每个被接受且改变战斗状态的回合都持久化，包括仅防御、恢复、逃跑、随机推进和30回合结束，不再含糊地区分“有无经济影响”。战斗不能持有另一份最终覆盖库存的可写副本；用药在当前角色库存上扣除，战斗快照可以记录相关只读展示量。战斗中的装备、地图外用药、调息及冲突修改必须由服务端拒绝。

开始战斗时固定`rules_version`、`config_hash`、双方基础属性和装备影响；升级恢复、任务奖励等仍在最终事务内按固定规则处理。持久化服务端专用`rng_algorithm_version`与随机状态/计数，随机推进随回合一起提交；事务回滚不能先推进唯一内存随机源，结果未知不能重新抽取。

跨语言对照样例注入预先指定的随机取值序列，不假设Rust与Godot相同seed会产生相同序列。Godot将底层随机算法视为实现细节，见[官方RandomNumberGenerator说明](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)。

部署新规则不能静默改写未结束战斗。保留旧规则读取/执行能力，或在维护中按已确认策略结束旧战斗；缺少旧规则时该角色进入受控恢复，而不是套用最新数值。战斗快照不包含随机内部状态。

动画只是结果播放，服务端先提交再返回。每回合有服务端最早接纳时间，自动与手动走同一校验路径；客户端播放期间锁输入，但服务器不信任动画完成通知。最小间隔可配置，恢复时不累积“补发回合”。30回合限制不代替真实时间限制。

按已确认D04，断线冻结60秒并停止自动下指令；超时按主动逃跑结束，保留已提交消耗、不发胜利奖励、不套用战败回城处罚；在线连续5分钟无有效指令同样结束。两项产品期限写入版本化配置，按持久化截止时间和状态版本触发一次超时结算。重连、心跳或无效指令不延后闲置截止时间。超时使用稳定的服务端操作ID；只在数据库可用、原在途回合已确定结束后处理。维护/可确认的服务端故障与玩家离线区分，不把服务端停机时间直接计作玩家违规挂机处罚。

## 7. 持久化、幂等与位置保存

建议逻辑表：`accounts`、`sessions`、`characters`、`inventory_items`、`quest_progress`、`personal_encounters`、`battles`、`battle_commands`、`reward_grants`、`operation_receipts`、`account_operation_receipts`、`currency_ledger`、`moderation_actions`。可对小型规则/战斗快照使用版本化JSONB，必须约束的身份、状态、计数和唯一键不得只藏在JSON中。

### 7.1 事务与数据库防线

| 对象 | 最低约束 |
|---|---|
| 操作回执 | `UNIQUE(character_id, operation_id)`；存操作类型、规范化请求摘要、终态、结果摘要与修订 |
| 账号级创建回执 | `account_operation_receipts`以`UNIQUE(account_id, operation_id)`去重；角色尚未创建时不能依赖character_id作用域 |
| 角色与昵称 | 当前 `UNIQUE(account_id,slot)` 与槽位 0～4 保证每账号最多五个；`UNIQUE(name_key)` 保证全服占名，唯一键不含地图或实例，见 [角色契约](characters.md) |
| 有效战斗指令 | `UNIQUE(battle_id, from_revision)`；仅成功接纳的指令占该修订 |
| 活动战斗 | 对未结束战斗的`character_id`建立部分唯一索引；角色active_battle_id需同事务维护 |
| 个人遭遇 | 身份键唯一，消费/预约需校验当前状态和所绑定battle_id |
| 奖励发放 | `UNIQUE(character_id, source_type, source_id, reward_key)`；来源由服务端生成，任务来源包含任务实例/阶段 |
| 库存/货币 | 归属外键、数量与余额非负、定义上限、装备实例唯一；背包容量也需角色串行检查 |
| 角色所有权与版本 | 写入条件含owner_epoch和相关修订；同事务推进变化的领域版本及state_revision |

部分唯一索引可只对符合条件的行强制唯一，见[PostgreSQL官方说明](https://www.postgresql.org/docs/current/indexes-partial.html)。不要误用普通唯一键让一个角色终身只能有一场战斗。

命令受理顺序以[协议第3节](protocol.md#3-持久化命令与幂等处理)为准：鉴权和结构校验→原回执/在途操作→新操作的业务校验→事务。应用层预查不能代替事务内唯一键争用和复核。相同operation_id、不同业务内容必须拒绝；更换operation_id也必须受业务来源唯一性保护。

购买的扣款/加物品、领奖的任务推进/货币/升级/恢复、有效战斗回合的战斗/资源/随机状态/回执均在同一事务完成。最终回合还包括奖励、个人遭遇和世界稳定状态。只有确认提交成功才发送成功响应；响应丢失不撤销已提交业务。

初期保留角色存续期间的紧凑去重终态和摘要；完整事件/大响应可按存储策略归档，但不得清掉去重依据后重新执行旧请求。归档回执返回确定终态和当前快照获取方式，不把归档当成“从未执行”。如以后需要删除去重记录，先实现服务器可验证的操作代际退休与旧代际拒绝，再定义清理策略；不能只靠客户端时间戳。

### 7.2 一致读取

在线角色的状态同步通过CharacterActor读取屏障，在上一个在途写入确定后取得同一提交的属性、库存、任务和活动战斗。数据库恢复读取使用同一个短`REPEATABLE READ READ ONLY`事务，再受控接管地图；不能把多个默认隔离级别查询当成一份一致快照。

PostgreSQL默认`READ COMMITTED`中同一事务的连续SELECT仍可能看见不同提交，见[事务隔离官方说明](https://www.postgresql.org/docs/current/transaction-iso.html)。数据库快照解决库内读取一致性，不自动解决地图内存状态；完整重连需要协议中的世界转换/同步屏障。只读快照事务不跨越网络发送过程。

### 7.3 位置持久化

| 类型 | 保存方式 |
|---|---|
| 普通移动 | 建议10～30秒分散保存、退出尽力保存；允许窗口内合法回退 |
| 开始/结束战斗、传送、战败回城 | 保存合法锚点并随业务事务推进world_epoch，不使用周期保存语义 |
| 旧位置任务迟到 | 仅在world_epoch相等且position_revision更大时更新；不能覆盖新世界归属 |
| 重启后的地图不存在或配置不匹配 | 受控恢复到规则允许的位置/实例，记录原因；不得默默分线或恢复到阻挡中 |

同一世界代次的position_revision在MapActor内单调递增并保存，重建时从已保存值继续；新world_epoch可开启新的位置版本域。普通位置写只修改位置字段，不提交整份角色快照覆盖装备、金币或任务。实际保存窗口包含调度积压和数据库延迟，不承诺仅等于定时器间隔。

### 7.4 昵称全服唯一与创建角色

D08已确认不允许线上角色重名。保留不可变character_id作为主键和权限依据，display_name用于显示，name_key用于全服唯一比较；昵称不是登录凭据，也不替代角色归属校验。离线存档及隔离测试数据库不参与生产线上占名。

服务端统一验证昵称并生成name_key，首尾空白不得形成另一名字，非法控制字符不能用来绕过查重。允许字符、长度与规范化的固定规则及正反样例在M0协议契约中固化；客户端提示、服务端校验和数据库比较必须使用同一规则。name_key不能依赖各客户端自行转换或部署环境中未固定的字符串比较行为；后续改变规范化规则须先审计已有名称冲突，再执行显式迁移，不能静默覆盖。

角色创建是账号级幂等事务：鉴权和结构校验→先查原账号操作回执→对新操作锁定账号并检查角色数量→校验昵称并插入角色及初始状态→原子提交创建结果与账号回执。数据库唯一约束负责并发抢名/同账号并发创建的最终防护，客户端可用性提示只是提示，不预留名字、不保证稍后仍可用。

不同账号并发抢同一 name_key 仅一个创建成功，另一方返回 `NAME_TAKEN`；同账号五槽已满返回 `CHARACTER_LIMIT_REACHED`。已成功创建的同 operation_id 重试先返回原 character_id，不因名字已被自己占用而报重名。同 ID 换昵称仍为 `IDEMPOTENCY_CONFLICT`；明确拒绝后改名是新业务意图，使用新 operation_id。唯一冲突须映射为稳定拒绝，不留下半个角色、初始资产或额外占名。

不自动给重名昵称添加数字/后缀，不自动改名后创建。首版不因此新增在线改名、角色删除或名称释放接口；封禁、断线、注销不会释放已创建角色的昵称。未来开放这些功能时必须沿用统一name_key、事务和占名规则。

## 8. 全链路背压、聊天与安全

### 8.1 资源边界

| 环节 | 要求 |
|---|---|
| 连接前/未认证 | IP/全局连接上限、短认证期限、低消息/字节预算；不加载角色或执行昂贵业务 |
| 移动入口 | 限流在寻路前；每角色有限待处理目标，合并旧目标，不能增加移动速度 |
| 地图循环 | 每轮消息处理有数量/时间预算，控制与迁移消息有保留预算，避免输入流饿死tick |
| 角色写入 | 每角色一个在途事务、有限待办；全局数据库写入信号量、连接池/等待/事务超时 |
| 位置保存 | 定时分散、同角色旧位置合并，不在同一时刻集中保存全部角色 |
| 发送 | 业务结果/实体生命周期可靠有界；只合并可替代的完整位置状态；慢连接超预算断开并重同步 |
| 客户端 | 限帧大小、解析深度/数组/队列、每帧应用预算与最长积压时间 |

10Hz是初始调度频率，不保证每帧准时。显式设置Tokio漏tick行为，避免默认`Burst`长时间补发；可采用`Skip`配合单调时钟和有上限的模拟子步。超长停顿停止本人路线并强制校正，不把累积时间兑换成突然远距离移动；广播只发当前状态，不追发过时的10Hz位置帧。漏tick策略含义见[Tokio官方API](https://docs.rs/tokio/latest/tokio/time/enum.MissedTickBehavior.html)。

队列限制同时按消息数、字节数和等待时长计量；有界应用队列之外还要配置WebSocket库、套接字和代理缓冲。已编号的可靠消息不能无提示丢弃；位置合并与序号分配按协议约定执行。

### 8.2 公共聊天

公共频道跨地图，身份、名称、时间取自服务端。初始建议128个Unicode标量值且最多512个UTF-8字节，禁止危险控制字符并按纯文本展示；字素簇等显示计数与服务器计数区别需要在UI解释。每账号建议2秒1条、突发3条，另设频道全局消息/字节/投递预算和公平调度，不让一个发送者耗尽额度。

同消息ID短期去重；拥塞时不成功接纳新消息，返回限流/忙碌，不无限广播排队。已经接纳的消息对慢连接按有界策略断开；历史不承诺断线期间全部补齐。D08中的运营项仍待确认客户端历史与服务端审计保留期，审计关联消息ID，不记录密码/票据。

### 8.3 认证与管理

密码用成熟Argon2id方案，哈希任务有独立并发上限，不阻塞异步地图任务。短期连接票据绑定登录会话和角色，原子消费；账号令牌、刷新令牌与票据均不得放普通日志或URL查询参数。

刷新令牌轮换、会话撤销/过期、账号封禁都要作用于已经建立的WSS，不只检查握手。受理业务前检查权限；已经受理的事务不因撤销消息丢失其结果，但撤销后不再接纳新操作。紧急管理变更走同角色协调，避免直改数据库与缓存冲突。

公网仅暴露TLS入口。数据库、指标、管理接口私网可达，管理认证/角色分权与审计单独处理。明确代理转发头信任范围，不能信任任意客户端X-Forwarded-For。浏览器客户端需要Origin允许列表；原生客户端不能把Origin当作身份证明。WSS长会话授权和资源限制参考[OWASP指南](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)。基础防护不表示具备大规模DDoS防御。

## 9. 容量预算而非人数承诺

D01已确认全服1000人正常混合游玩，单实例热点单独验证和报告；D02已确认首版不自动分线、不按人数隐藏本应可见的玩家，不以减小互见范围替换容量目标。容量分别报告全服混合游玩、单实例热点和真实客户端显示能力。32×32地图不能靠AOI（附近实体可见范围）自动消除所有人聚集的最坏情况。

静态预算示例，不是实测：若N人全部互见、全部移动、同步频率f，每个实体更新平均s字节，则服务器下行约为`N × (N - 1) × f × s`字节/秒。N=1000、f=10、s=100时为999,000,000字节/秒，约999 MB/s或7.992 Gbit/s，未计TLS、协议头、重传及其他业务。必须用实际JSON编码测s，批处理能降低封装和系统调用开销，不会自动消除投递规模。

公共聊天同样需要总预算：1000人都按每2秒1条发送，会达到约500条/秒、50万次接收投递/秒（按每条发给1000个接收者估算）。这不是正常聊天负载，而是合法个人限额叠加的压力上界。

优化顺序：静止不发→批量/复用编码→可见范围→路线变化同步及稀疏校正→位置合并→基于压测决定二进制协议。路线上报变化不是允许客户端决定路线；丢失最新状态仍由权威快照校正。图集与动画资源共享，姓名牌更新按需；渲染优化不得擅自隐藏产品要求可见的角色。具体负载和SLO集中在测试计划中。

## 10. 发布、故障与备份

健康检查分存活与就绪：数据库或关键恢复不可用时不能继续接受会产生未知结果的新角色业务。停机先停止新会话/新业务，有限等待在途事务，能确认回滚的才中止，保存合法位置并通知维护；强杀后根据已提交状态恢复。

发布先验证协议/配置/数据库迁移兼容性，备份并演练恢复，再维护窗口单写切换。应用回退不等于数据库可以无条件回退；破坏性迁移需独立方案。旧活动战斗规则缺失是发布阻断项。

| 故障范围 | 保证与边界 |
|---|---|
| 网络断开、游戏进程崩溃，数据库及持久存储完好 | 已确认的经济/任务/战斗提交不丢；位置可按保存窗口合法回退 |
| 数据库短暂不可用 | 经济修改拒绝或进入恢复中；不在内存继续结算后假报成功 |
| 数据库主机/磁盘损坏 | 依赖经验证的备份/WAL归档/副本策略，不能由单数据库方案宣称零丢失 |
| 从历史备份恢复 | 按D07确定最大可接受数据损失量（RPO）和恢复时间（RTO）；恢复时间点以前/以后的业务必须清楚披露 |

生产确认成功要求启用与承诺一致的数据库持久化设置，不以关闭同步持久化换取容量成绩。备份需要加密、独立保存、保留策略和恢复演练；聊天审计及个人资料保留遵循D08确认规则。本设计不替代素材授权审查：公网发布前核验原包素材来源与授权，未核验不能标记为已获授权。
