# 联机协议草案

状态：逻辑契约草案，尚无已实现接口。字段、路由与限额需在实施前用契约测试冻结。

## 1. 传输与鉴权

- HTTPS处理注册、登录、刷新/撤销会话、角色列表、创建角色和申请游戏连接凭据。
- WSS处理角色进入世界后的移动、聊天、任务、背包和战斗操作。
- 初期使用UTF-8 JSON；确有压测证据后再评估二进制协议。
- 建议通过已认证HTTPS接口取得短时、单次使用、绑定会话的连接票据，在WSS建立后的首条认证消息中交换；认证超时立即关闭。
- 不把长期令牌放在URL查询参数中，不把票据或令牌写入普通日志。
- 票据验证、角色归属和重复上线检查通过前，连接不能订阅地图或公共聊天。
- 协议握手携带客户端协议版本与配置版本；不兼容时明确拒绝，不带着错误地图继续运行。

## 2. 消息封装与版本

客户端操作示例：

```json
{
  "protocol_version": 1,
  "type": "battle.command",
  "request_id": "req-001",
  "operation_id": "op-001",
  "payload": {
    "battle_id": "battle-001",
    "expected_revision": 3,
    "command": "attack"
  }
}
```

- `request_id`用于一次请求与响应关联，不自动提供业务幂等。
- `operation_id`用于需要重试的业务修改；重试必须保留原值，不能每次重新生成。
- 幂等键绑定认证主体、操作类型和请求内容；同键不同内容必须报错。
- 货币、物品、任务领奖、战斗指令等关键操作的回执与业务修改一起持久化。
- 移动使用连接内递增序号，聊天使用短期去重与限速，不要求每次位置更新持久化。
- 状态版本按角色、背包、战斗等领域分别维护，不能用地图位置版本使所有业务请求互相冲突。

响应示例：

```json
{
  "protocol_version": 1,
  "type": "response",
  "request_id": "req-001",
  "ok": true,
  "payload": {
    "battle_id": "battle-001",
    "revision": 4,
    "events": []
  }
}
```

错误返回稳定错误码，例如`UNAUTHENTICATED`、`CHARACTER_BUSY`、`STALE_REVISION`、`INVALID_TARGET`、`INSUFFICIENT_RESOURCE`、`RATE_LIMITED`和`SERVER_UNAVAILABLE`。客户端不能靠匹配中文提示判断业务分支。

推送事件带明确的流标识和递增序号，例如地图实例流、个人战斗流、公共聊天流。不同流不要求全局排序；切图、重连后不得继续应用旧地图流的事件。

协议需定义ID和计数的JSON表示范围。建议ID使用字符串，避免跨语言JSON数字精度差异。限制消息大小、数组长度、坐标与数值范围，拒绝非有限数和未知危险操作。

## 3. 主要操作

下表为拟议消息名，不表示现有代码已经支持。

| 操作 | 客户端发送 | 服务端返回或推送 |
|---|---|---|
| 进入世界 | `world.enter` | 本人快照、地图实例、可见玩家、个人任务目标、活动战斗 |
| 移动目标 | `world.move_to` | 接受的路线/目标、输入确认序号、权威位置 |
| 停止移动 | `world.stop` | 合法停止状态，按当前格子移动规则处理 |
| 地图变化 | 无需客户端提交他人数据 | `entity.enter`、`entity.update`、`entity.leave` |
| 公共聊天 | `chat.send` | `chat.message`或拒绝原因 |
| NPC/怪物交互 | `world.interact` | 对话选项、任务结果或战斗进入事件 |
| 接受/领取任务 | `quest.accept`、`quest.claim` | 新任务版本、奖励和属性变化 |
| 背包操作 | `inventory.use/equip/unequip/buy/discard` | 权威背包版本与资源变化 |
| 战斗指令 | `battle.command` | 新战斗修订及本回合事件 |
| 查询恢复 | `state.sync` | 对应领域权威快照 |
| 心跳 | `ping` | `pong`及服务端时间 |

所有目标ID都需要校验是否属于当前实例或本人任务。客户端不能发送金币增量、伤害值、击杀结果或奖励内容作为权威输入。

## 4. 移动与地图同步

首版采用服务器管理路线的格子移动：

1. 点击提交目标格；键盘提交短目标，不能以高频请求增加实际移动速度。
2. 服务端校验当前地图、格子边界、阻挡、移动/战斗状态，生成或验证路线。
3. 服务端基于自身时钟和角色速度推进位置，不使用客户端时间差计算可移动距离。
4. 客户端进行局部预测，收到权威位置、已处理输入序号和路线状态后校正。
5. 服务端向附近玩家发送增量更新，远端客户端插值播放。

客户端可以显示亚格子位置，但服务器必须统一格子中心、路线切换及停止语义。当前位置、已到达格子、目标格不得各自独立修改。

地图快照包含`map_id`、`instance_id`、配置版本与地图流序号。服务端更新可先以10Hz为起点，客户端动画帧率与网络更新频率解耦。

可见范围变化发送实体进入/离开，不把全服角色列表反复发送给每人。消息过大时分批发送快照，不能无限放宽帧大小。

## 5. 公共聊天

`chat.send`只需携带客户端消息ID、频道和纯文本内容。首版仅允许公共频道，频道资格由服务端决定。

服务端消息包含：消息ID、发送者角色ID、显示名称、服务端时间、频道、文本内容。客户端不能覆盖这些身份字段。

- 服务端先做长度、字节数、控制字符、禁言和频率校验，再广播。
- 重试使用相同客户端消息ID，短期去重，避免显示重复消息。
- 首版建议只提供有限近期历史；断线期间的所有聊天消息不保证补发。
- 客户端聊天记录设置条数上限，不无限积累节点和字符串。
- 审计记录、举报标识和禁言操作关联消息ID，具体保留期在公网发布前确定。

## 6. 独立PVE与事件播放

服务端战斗流程与客户端播放流程分离：

```text
校验指令和expected_revision
  → 计算玩家行动、敌方行动、回合结算
  → 原子提交状态、资源变化、操作回执和必要奖励
  → 返回新修订与有序事件
  → 客户端按事件播放并更新界面
```

事件可包含技能使用、资源消耗、伤害、恢复、回合结束、胜败和奖励。每个事件标明行动者、目标和必要结果，客户端不重新随机计算伤害。

- 服务端不等待客户端动画完成确认后才保存结果。
- 客户端播放期间锁定该回合输入；服务端也必须校验指令节奏和回合版本，不能只依赖客户端锁定。
- 查看和无效操作不推进回合；重复操作返回原结果，旧版本的新操作拒绝。
- 战斗快照包含战斗ID、修订、回合、双方状态、可接受指令和是否结算完成。
- 重连可直接恢复最新快照，未播完的旧动画可以跳过；业务结果不能依赖动画是否播完。
- 服务端超时处理同样走幂等事务，不因断线重复发奖或回滚已消耗道具。

## 7. 重连与错误处理

- WSS断开后使用退避与随机抖动重连，不能所有客户端固定间隔同时重试。
- 长期会话仍有效时，通过HTTPS申请新的单次票据；不重复使用已经消费的连接票据。
- 重连后刷新角色、地图、背包、任务和活动战斗快照，再接受操作。
- 经济类请求结果未知时，按原`operation_id`查询或重试，不能通过新操作重复购买。
- 角色被封禁、凭据过期或重复上线不无限自动重试，应展示明确原因。
- 旧连接的迟到消息通过会话代次和地图流标识拒绝。
- 位置更新可以被新快照替代，关键业务结果不得仅靠不可恢复的推送传递。
