# 多平台接口层与移动浏览器导出方案

设计修订：2026-10-16。状态：P1七类接口已分步接入原生基础实现，包括配置/存储、显示、生命周期、资源准备、输入焦点/组合状态检查及系统退出请求；P2a已接入服务端精确Origin白名单，见[来源安全前置](../tests/web_origins.md)。Windows实际运行和P2整体～P4仍待验收。其他实现边界与记录见[平台基础](../tests/platform_interface.md)、[资源准备](../tests/platform_resources.md)、[输入与系统动作](../tests/platform_input_actions.md)，不代表完成Web导出或通过手机真机测试。

用户目标：后续支持多平台导出，建立对应的`interface`目录；首期让iOS和Android手机通过默认浏览器打开链接游玩。产品范围见[设计入口D09](README.md)，离线/在线业务边界见[architecture.md](architecture.md)，认证与世界协议继续遵循[protocol.md](protocol.md)、[auth.md](auth.md)和[shared_world.md](shared_world.md)。本文不替代这些契约，也不调整D01～D08的既有决策。

## 1. 目标、范围与支持口径

采用一套游戏逻辑、一套资源、一套网络协议，通过平台接口实现多平台导出。首期只交付一个Web导出包，iOS和Android浏览器共用，不分别维护两套游戏。后续按实际需求增加Android、iOS、Windows、Linux、macOS原生导出。

| 项目 | 首期方案 |
|---|---|
| iOS浏览器 | 以Safari为首要验收环境；其他被用户设为默认的浏览器不能未经测试就宣称支持 |
| Android浏览器 | 以Chrome为技术基线，并验收目标机型的实际默认/出厂预装浏览器 |
| 使用方式 | 打开HTTPS链接即可游玩，不要求安装应用或添加到主屏幕 |
| 导出方式 | Godot Web、Compatibility渲染、单线程；具体选项以锁定的引擎和导出模板为准 |
| 布局 | 首期沿用320×480竖屏逻辑坐标，等比缩放到可用区域 |
| 联机 | HTTPS接口和WSS世界连接，共用现有票据及业务协议 |
| 原生客户端 | 保留现有Linux、Windows导出预设与行为，作为回归范围 |
| 暂不保证 | 微信/QQ等内嵌浏览器、未验收的厂商浏览器、老旧系统与老旧浏览器 |

“默认浏览器”不是固定产品名称。Safari/Chrome是首期验证基线，不等于覆盖所有用户选择和所有厂商浏览器。实施时记录设备、系统、浏览器及版本，形成明确的“通过/有条件通过/不支持”名单。最低系统与浏览器版本待真机验证后冻结，不在本方案中虚构下限。

首期非目标：重写JavaScript游戏客户端、把原始`gameonline.ext`或MRP运行时直接搬进浏览器、恢复原版服务端、应用商店上架、复杂PWA缓存、远程分包下载、增加新的玩法及数值规则。网页化对象是已经重建的`client/`，与原客户端逆向工作独立。

管理工具边界：`scenes/admin/`及其专用脚本仅在PC原生桌面运行，不属于Web/手机适配或浏览器验收范围，也不进入游戏导出。平台化只迁移游戏的真实调用方，不为admin增加网页实现。

## 3. 架构边界

```text
页面、HUD、地图与战斗界面
    ├── GameService → OfflineAdapter / OnlineAdapter → NetworkClient → HTTPS/WSS
    └── Platform    → 接口契约 → Common / Web / Native平台实现
```

`GameService`负责玩法请求和业务快照；`Platform`只负责运行环境差异。网页同样可以有离线/在线双入口，原生客户端同样可以联网，二者不是互斥的适配器。

页面和业务模块通过`Platform`获得平台能力，不散布Safari、Android、Windows等判断。`network/`仍负责登录、票据、世界同步、心跳与重连；不为Web重写第二套HTTP/WebSocket业务，也不将认证和世界协议移到JavaScript。

平台实现不得直接修改等级、背包、奖励、任务或在线角色状态，不引用具体地图/战斗场景控制游戏流程。它可以上报“恢复前台”“存储失败”等事件，业务层再按既有规则处理。

所有平台专有API集中在适配层。签名、证书、商店提交属于构建发布层，不放入运行时`interface`，更不能进入公开Web包。

## 5. 接口职责与契约

只抽象真实的平台差异，不把整个Godot API再次包装。以下名称和操作为目标契约，具体签名在实施阶段结合现有调用方冻结。

| 接口 | 负责 | 不负责 |
|---|---|---|
| `DisplayInterface` | 可用区域、安全区、尺寸变化、坐标转换和显示能力 | 背包格子规则、战斗业务布局 |
| `TextInputInterface` | 焦点、中文输入协作、软键盘、可选HTML输入桥接 | 昵称唯一性、聊天审核 |
| `LifecycleInterface` | 激活、隐藏、恢复、失焦、页面恢复事件 | 自行决定登录、重连、处罚或发奖 |
| `StorageInterface` | 本地数据读写、存储状态、持久化状态、导入导出 | 在线数据库、密码管理、账号认证 |
| `ResourceLoaderInterface` | 资源准备、缓存复用、进度、取消、失败 | 战斗输赢、奖励选择、服务端资源权威 |
| `RuntimeConfigInterface` | 服务入口、构建版本、受控运行配置来源 | 私钥、服务端密钥、玩家密码 |
| `SystemActionsInterface` | 退出请求、音频启用、全屏请求、复制等平台动作 | 保存/结算、具体游戏操作和业务状态机 |

### 5.1 初始化与依赖

`platform_factory.gd`先选择Web或原生实现，再检测能力、应用策略，组装只读上下文与各接口。`Platform`可作为自动加载入口，但必须显式提供就绪/失败状态；依赖配置的`Game`、`OnlineAccount`和页面不能仅依赖自动加载顺序推断异步初始化已经完成。

初始化流程：`未初始化 → 初始化中 → 就绪/降级可用/失败`。失败提供可读原因，不能进入无响应黑屏。适配器不得反向依赖`Game`或`OnlineAccount`，避免自动加载循环。

浏览器版本先按Web运行目标选择适配器，不能用原生`ios`/`android`导出特性标签判断手机浏览器。能力检测优先于UA判断；必要的设备兼容提示与能力判断分开。相关Godot特性标签含义见[参考资料R2](#12-实施参考资料)。

### 5.2 能力与操作结果

上下文区分静态能力、动态状态和本次调用结果。例如“存在全屏API”“当前不是全屏”“此次请求被拒绝”是三个不同事实。动态状态变化通过信号通知，避免只在启动时检测一次。

可能涉及浏览器交互的操作支持异步结果，至少区分成功、不支持、用户拒绝、暂时失败、取消及数据无效。错误同时具有稳定代码和可显示信息；不得将“不支持”静默当作成功。

并发请求使用请求标识和调用方代次。取消或场景销毁后可以停止等待，但不得让旧回调修改新场景；不承诺所有底层操作均能物理中止。回调订阅随对象释放而解绑，JavaScript回调引用和事件监听由Web适配器统一管理。

需要即时用户手势的动作应在相应交互回调中发起，不能先统一排队、等待任意异步任务后才尝试全屏、音频启用或剪贴板调用。调用失败必须可恢复。

## 6. 移动浏览器适配

### 6.1 显示、安全区与坐标

保留320×480逻辑区域并等比居中显示，不在首期全面重排所有界面。网页外壳计算实际可用区域及安全区，Godot负责游戏画布到逻辑坐标的映射；同一安全区不能在CSS和Godot重复扣减。

接口应明确区分CSS像素、画布像素与游戏逻辑坐标，统一处理设备像素比和缩放。地址栏伸缩、横竖屏变化、软键盘和窗口大小变化均触发区域更新，不通过写死某款手机尺寸处理。视觉视口相关行为实施时参照R4。

旋转后不得裁掉登录、确认或返回按钮。首期以竖屏体验优先，横屏可等比居中留边；不把强制方向锁或全屏成功作为可玩的前提。键盘弹出时优先保证当前输入框、确认和取消操作可见。

### 6.2 触摸与输入

普通按钮、点击、拖动继续采用Godot输入系统，不重写另一套通用触摸框架。检查地图、背包、封面、弹窗、滚动区域和小地图，确保不依赖悬停、滚轮或实体键盘。

明确触摸与模拟鼠标的主处理路径，避免一次手势触发两次操作。网页手势限制只作用于需要的游戏区域，保留输入框选择、粘贴及合理的页面可访问性。拖动中丢失焦点或切后台时清除持续输入，恢复后不能保留“按住移动”。

中文输入先验证原有Godot控件，覆盖组合输入、候选词确认、删除、粘贴、失焦与键盘收起。候选词尚未提交时不得提前发送聊天或创建角色。实测无法解决时才由`TextInputInterface`切换HTML输入桥接；密码和令牌不得进入桥接诊断日志。JavaScript桥接范围见R3。

### 6.3 音频与全屏

入口提供点击开始动作，用于启动游戏并尝试启用声音；全屏是单独可选操作。普通网页模式必须完整可玩，拒绝音频/全屏后保留恢复入口，不反复弹出授权请求。具体限制按锁定浏览器实测，参考R1。

### 6.4 前后台、页面回收与重连

生命周期接口统一上报事件，网络业务执行恢复：`恢复前台 → 校验会话 → 必要时重新申请票据 → 重连 → 完整同步屏障 → 恢复输入`。隐藏时不能承诺后台心跳持续运行，浏览器计时与可见性行为参考R5。

恢复流程应幂等，重复恢复事件只能触发受控的单次重连；连接代次、快照和操作回执沿用现有协议。停止陈旧移动输入，不补发离线期间累计的操作，不因网络恢复自动重复提交战斗命令。

D04的60秒断线窗口及5分钟闲置规则继续由服务端计时。切后台、反复打开页面或生命周期事件不能延长该窗口，也不能在平台接口中新增宽限或处罚。D03的同会话重连接管、不同会话拒绝第二次上线规则保持不变。

页面被回收后按冷启动处理，不依赖一定执行退出/保存回调。首期保留现有凭据边界，不新增浏览器令牌持久化；若页面回收后凭据已丢失，应提示重新登录，不宣称可以无感恢复认证。

### 6.5 本地存储

保留离线与在线入口，但离线存档只能恢复离线角色，不自动导入线上。已有存档结构、版本校验和玩家规则由业务层掌握，存储接口负责平台读写和错误映射。

必须区分文件写入成功、虚拟文件系统更新、持久化同步状态和后续会话可恢复性。不能把内存中的写入成功统一显示成“永久保存”。现有同步返回值改为异步契约时，应一并迁移全部调用方和提示流程，不静默改变语义。

提供用户主动导入/导出离线存档的路径；导入限制大小并校验结构，浏览器不支持或用户取消时明确反馈。浏览器配额不足、清理数据或拒绝持久化时允许受控降级，并提示丢档风险。参考R6；不承诺数据永久不被清理。

公开配置、URL、存档、页面日志均不保存密码、令牌或服务端秘密。在线资产继续由服务端持久化和权威校验。

### 6.6 资源准备与性能

`ResourceLoaderInterface`统一资源准备请求、缓存、进度、失败与取消。原生侧先保留已验证的加载行为；Web单线程侧针对锁定引擎实测`load_threaded_*`的行为，不把API名称直接当成一定支持或一定失败的证据。

必要时采用启动预热、逐资源/逐帧准备策略。分帧不保证单个大型资源解码可被中断，因此还需测量最大单项耗时，必要时减小图集、预先准备或调整资源组织。进度表示实际工作量，不伪造下载完成率。

首期准备已有包内资源，不同时引入远程分包系统。按需加载不是按需下载；完整PCK中资源即使延迟实例化，也可能仍需先下载。确认首包和内存问题后，再独立设计分包、清单、哈希校验与缓存策略。

D02不允许通过静默隐藏玩家、减少应互见范围来掩盖手机性能不足。性能策略可以调整渲染分辨率、装饰特效和加载方式，但不得改变权威状态、玩法可见性或业务规则；具体降级需记录和验证。

## 8. 网页联机、来源与安全

### 8.1 Origin处理

P2a已将原先一律拒绝的逻辑改为显式可信网页来源白名单，配置及验证见[来源安全前置](../tests/web_origins.md)。默认配置仍拒绝一切携带`Origin`的请求；同域部署不会自动放行。浏览器握手行为参照R7。

白名单按规范化的协议、主机和有效端口精确匹配，正式和本地开发来源分开配置。不使用任意通配、字符串包含、删除Origin或全部放行作为兼容修复；默认拒绝未知来源、`null`来源及异常多值。开发调试仅开放明确的测试来源。

缺少Origin的原生路径仍按原生认证契约处理；Origin不作为身份凭据，不能因为来源匹配而跳过票据校验、协议版本、角色所有权、限流和消息大小限制。该策略同时需要正向和反向验收。

继续使用HTTPS获取单次票据，再在WebSocket首包执行`auth.exchange`。票据不进入URL、公开配置或日志，不改为依赖浏览器不可统一设置的自定义WebSocket认证头；接口限制参照R8。

### 8.2 同域部署与配置

| 公网路径 | 用途 |
|---|---|
| `/` | 游戏入口与能力检查 |
| `/game/` | Godot导出的HTML、JavaScript、WASM、PCK等静态文件 |
| `/api/v1/` | 现有HTTP接口 |
| `/api/v1/world/ws` | 现有WebSocket入口 |

正式入口统一HTTPS/WSS，反向代理转发游戏接口和WebSocket升级。页面静态资源可以位于`/game/`，API根仍按受控配置独立确定，不能错误拼成`/game/api/v1/`。

浏览器默认使用当前站点的受控服务地址；原生客户端保留现有服务器选择能力。正式网页不从任意查询参数接收认证服务地址，不向非预期服务发送凭据。仅需要公开的数据进入运行配置。

首期同域避免额外HTTP跨域配置。未来确需跨域时再明确HTTP CORS预检、允许来源/方法/请求头及凭据策略；CORS配置不能替代WebSocket Origin校验。浏览器离线入口仍是本地离线玩法，不意味网页可以任意访问手机或局域网中的HTTP服务。

数据库、只读监控和管理接口不因新增游戏网页而公开；现有回环监控端口的边界保持不变。

## 9. 导出、版本与发布

新增一个Web预设，共享同一客户端工程。锁定实际Godot版本、对应导出模板和依赖；`project.godot`中的特性标识不是实际已安装版本的验证。首期选择Compatibility和单线程，不启用项目不需要的扩展。

维护`client/web/shell.html`模板和其资源，保证模板引用的CSS/JavaScript在发布产物中可访问；不手工改导出后会被覆盖的HTML。动态加载的JSON、角色元数据、图集、字体和必要场景应逐项核验包含；管理场景、测试、分析材料、依赖目录和密钥排除。

HTML、JavaScript、WASM、PCK以同一构建标识作为完整版本发布/回滚。采用版本化资源位置或等效的一致发布方案，禁止入口先更新但包仍来自旧版。配置正确的MIME类型、压缩和缓存策略；压缩前后资源类型保持正确。参考R1。

引导页应在运行引擎前尽可能检查必要能力，并处理WASM/WebGL初始化失败、资源下载失败及重试；能力检测通过仍不等于完整运行已经验收。避免仅显示空白画布。

首期不增加复杂Service Worker/PWA缓存，基础流程稳定后另行设计“添加到主屏幕”、缓存升级和回滚。静态资源离线可用不等于联机玩法可离线运行，API认证和票据不进入离线缓存。

构建版本、配置摘要与协议兼容性继续分开管理。不同客户端版本同时存在时按服务端协议约束处理，不用强制缓存清空掩盖协议不兼容。

## 10. 实施阶段与验收门槛

使用P1～P4作为平台化工作编号，不替换[roadmap.md](roadmap.md)现有M0～M5业务路线。平台化不能把尚未实现的玩法标为完成，网页的完整业务验收依赖对应业务阶段。

| 阶段 | 工作范围 | 退出条件 |
|---|---|---|
| P1：接口基础 | 建立入口、契约、原生公共实现；迁移配置和存储差异 | 旧离线存档可读；现有原生启动、输入、存储和联机行为无回退 |
| P2：Web最小闭环 | 单线程预设、网页外壳、资源准备、同域入口、Origin白名单 | 浏览器可启动；完成离线地图/战斗/存档；完成当前已实现的登录、角色、入场和世界同步流程 |
| P3：手机适配 | iOS与Android实际浏览器的触摸、安全区、中文输入、音频及前后台恢复 | 无实体键盘即可完成主要操作；中文输入不重复提交；锁屏/切换后按协议恢复或明确重新登录 |
| P4：发布与回归 | 弱网、页面回收、存储异常、资源版本、真机性能与旧平台回归 | 支持名单明确；失败可解释；更新不混包；不重复事务、不损坏存档、不改变D01～D08规则 |

P1可以与现有业务开发并行，但应避免同时改动同一关键文件。P2依赖现有认证/世界接口；线上PVE或其他玩法尚未完成时分别标记阻塞，不以离线战斗代替线上通过。P4与M5公网发布门槛汇合，不能因能在手机打开页面就跳过安全、容量和恢复验证。

### 10.1 必测矩阵

| 类别 | 验收场景 |
|---|---|
| 平台 | iPhone Safari；Android Chrome；目标机型默认浏览器；原生Linux/Windows回归；其他环境按名单记录 |
| 显示 | 刘海/手势区、长屏、地址栏展开收起、横竖屏、软键盘遮挡、坐标点击准确性 |
| 输入 | 地图移动/拖动、背包滚动、弹窗关闭、中文候选词、密码输入、粘贴、失焦取消 |
| 生命周期 | 短时切后台、超过D04窗口、锁屏、页面回收、重复恢复事件、凭据丢失后的重新登录 |
| 网络 | Wi-Fi/蜂窝切换、弱网、断网、认证过期、票据失败、快照中断及未确认事务恢复 |
| 安全 | 白名单Origin成功；未知/null来源拒绝；无Origin的原生连接仍须认证；错误票据/版本/角色归属拒绝 |
| 存储 | 正常写入与重开恢复、不可持久化、配额/写入失败、数据被清理、导入取消及非法存档拒绝 |
| 发布 | 首次加载、重复访问、资源失败重试、版本切换、旧页面重连、完整版本回滚 |
| 性能 | 首包传输量、首屏/入场耗时、帧耗时、卡顿、资源准备峰值和可测内存；记录设备与测量方法 |

真机测试不能由桌面设备模拟器替代。具体系统下限、性能预算和通过阈值在冻结的设备/浏览器矩阵下测量后确定；无法可靠测量的指标标注未知，不把压缩包大小当作运行内存。至少包含一台性能较低的目标Android设备。

这里只定义设计验收门槛。可执行测试、命令、设备实测日志和结果按仓库现有约定归入`tests/`，不在设计中编造通过记录。

## 11. 后续多平台扩展与未决项

后续原生Android/iOS优先复用`native/`和公共实现，只有安全区、系统输入、文件选择、系统存储等确有差异时才增加专用模块。Windows/Linux/macOS同理，不复制游戏资源和网络业务。平台SDK、构建证书和商店渠道配置由发布层管理。

实施前需要冻结的技术项：实际引擎/模板版本、Web导出选项、默认浏览器验收名单、最低系统版本、资源加载策略和可测性能预算。部署域名、地域、预算、备份恢复继续按D07处理；账号恢复和管理权限继续按D08处理。它们不阻止先搭建接口和本地验证，但相应未决项必须在正式发布前解决。

本设计不授权自动提交、推送、重写历史或清理分支。现有`main`、`dev`及未提交文件保持原状；实施中的Git操作按用户单独要求执行。
