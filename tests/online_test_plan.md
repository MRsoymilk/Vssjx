# 联机版测试与容量验收计划

状态：待执行计划，Rust服务端及联网功能尚未实施，没有1000人容量结论。产品范围见[设计入口](../design/README.md)，实施阶段对应[roadmap.md](../design/roadmap.md)。当前客户端测试入口见[testing.md](testing.md)。

现有离线存档不得被联机测试覆盖。测试账号、数据库和存档全部隔离；迁移工程时同步调整测试路径、离屏工具和固定规则样例。

## 1. 各阶段验收

### M0：目录、配置与契约

- 原有离线流程、Python素材测试、Godot自动测试、六角色运动回归和真实渲染离屏测试通过。
- 不覆盖现有玩家存档；启动器仍能识别其他项目，游玩统计仍关联原游戏ID。
- 工程迁移后命令、UID和资源路径正确，首轮版本化协议有固定规则与契约样例。

### M1：服务骨架与账号角色

- 两个账号的数据互相隔离；未认证或错误归属的请求被拒绝。
- 服务重启后角色仍存在，密码和令牌不进入日志。
- 测试环境可从空数据库通过版本化迁移建立。

### M2：多人进入同一地图

- 两个真实客户端进入同一实例互相可见，进出与切图无残影。
- 不能穿墙、超速或绕过传送限制。
- 丢包、延迟、断线后可恢复一致位置，不接收旧会话和旧地图的迟到更新。
- 不把其他玩家的私有数据发送给客户端。

### M3：公共聊天

- 不同地图可以互发公共消息，不能伪造发送者身份或注入富文本。
- 刷屏受到限制，重复请求不重复显示同一消息。
- 慢客户端不会阻塞其他玩家或无限占用内存。

### M4：个人任务、背包与PVE

- 在线完成“领任务→三只山狼→领取奖励→遗迹妖王”。
- A击杀自己的任务怪不影响B。
- 重复请求和并发操作不能复制道具、货币或奖励；战斗与背包不能争用同一份库存。
- 服务重启后战斗关键状态可恢复。
- 覆盖“事务提交后、推送前断线”和“最终回合完成后、客户端确认前重启”等故障点，不仅验证正常流程。

### M5：公网部署与容量

- 使用压测机器人、离屏联网客户端验证部署环境。
- 在明确记录的机器、网络和数据库配置上完成约定负载。
- 公开延迟分位数、资源消耗、错误率和故障恢复表现，不能仅写“支持1000人”。
- 完成备份恢复、优雅停机与集中重连演练。

## 2. 自动化测试分层

| 层次 | 主要内容 |
|---|---|
| Rust规则单元测试 | 属性、消耗、战斗、任务、固定随机源、边界值 |
| 数据库集成测试 | 迁移、约束、事务回滚、幂等、奖励唯一性、重启恢复 |
| 协议契约测试 | Rust/Godot字段一致、版本不兼容、非法消息、大小与频率限制 |
| 双客户端测试 | 同地图可见、私有怪物隔离、聊天、切图、掉线重连 |
| Godot无渲染测试 | 网络状态机、业务快照和错误处理 |
| 真实渲染离屏测试 | 多人模型、插值、移动步伐、聊天界面、战斗事件播放 |
| 压测与故障测试 | 1000人负载、慢连接、数据库异常、重启和集中重连 |

`--headless`使用虚拟渲染，不能代替真实截图验证。Linux真实渲染使用Xvfb与OpenGL/Mesa；大量负载由不渲染的协议机器人承担，不以1000个Godot窗口作为主要压测方式。

## 3. 容量口径

已确认目标为1000人同时在线，但全服/单实例以及分线规则尚未确认。

- 1000条空闲连接只证明连接维护能力。
- 1000人正常游玩需要移动、聊天、PVE和数据库写入的组合负载。
- 1000人集中在同一可见范围属于单独热点场景，不能用分散地图的结果替代。
- 如最终采用分线，报告必须说明每线人数和互见范围，不能声称已经验证1000人同图互见。

## 4. 测试环境记录

每次报告记录代码提交、配置版本、Rust/数据库版本、CPU/内存、系统、网络、数据库位置、机器人位置、地图/实例数量、TLS与代理配置。

不能只在同机回环网络上推断公网体验。需要增加可控延迟、抖动、丢包及慢客户端场景。

## 5. 压测步骤

1. 按50、200、500、1000人逐步增加负载，观察拐点。
2. 分别测试空闲心跳、持续合法移动、人员进入/离开和切图。
3. 测试正常发言、突发公共广播和超过限额的恶意消息。
4. 测试独立PVE与关键业务并发提交、奖励结算和请求重放。
5. 测试人员集中热点；若分线未获确认，不以自动分线掩盖热点问题。
6. 测试发送队列拥塞、数据库暂时不可用、服务重启和集中重连。
7. 建议目标混合负载稳定运行至少60分钟，再执行更长时间的内存与连接泄漏观察。

混合负载的移动比例、战斗比例、指令间隔、聊天频率和上下线速率应在测试前冻结，并写入机器人配置。在线人数与“同时有操作的人数”分别报告。

## 6. 关键指标与门槛

- 在线人数、认证成功率、重连成功率与恢复耗时。
- 指令处理延迟p50/p95/p99，端到端延迟与服务器内部延迟分开记录。
- 地图tick耗时、超期比例、输入积压和可见实体数量。
- 聊天广播延迟、消息速率、队列水位、慢连接断开次数。
- 战斗指令/最终结算延迟、重复请求命中数、重复奖励数。
- CPU、RSS、任务/连接数量、网络吞吐、数据库连接池与事务等待。

建议初始性能门槛为服务器内部普通指令处理p95不超过100ms、10Hz地图循环不持续积压；这是待在环境与负载冻结后确认的目标，不是现有性能结论。

一致性门槛：重复奖励为零；确认成功的货币、物品和任务变更在恢复后不丢失。位置允许在约定保存窗口内回退，但不能恢复到阻挡或非法地图。

## 7. 产物归档

测试说明、用例、容量方案及需要提交的测试报告统一放在`tests/`下；本地大量截图和日志可输出到`/tmp/opencode/`等独立目录。不要把测试命令、结果或验收方案写回README。

本计划目前没有可执行的Rust服务端或联机压测命令；对应模块实施后再补充实际入口，不将设计草案当作已经通过的测试结果。
