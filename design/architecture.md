# 联机架构设计

状态：Rust方案草案。产品范围与待确认事项见[设计入口](README.md)。

## 1. 当前代码与迁移目标

当前项目是Godot离线原型，角色、任务和战斗数据由客户端掌握：

| 当前路径 | 当前职责 | 联网后的分工 |
|---|---|---|
| `scripts/game_state.gd` | 属性、背包、升级、任务、本地存档 | 权威业务迁到服务端；客户端保留展示快照和离线适配 |
| `scripts/battle.gd` | 回合计算、随机数、奖励落盘 | 服务端计算与保存，客户端播放事件 |
| `scripts/world.gd` | 地图、阻挡、寻路、巡逻、交互 | 服务端校验与同步，客户端负责输入、预测和渲染 |
| `scripts/main.gd` | 页面、业务调用、战斗表现 | 页面保留，逐步通过业务接口发送操作 |
| `scripts/inventory.gd` | 背包展示与本地操作 | 展示权威快照，操作改为请求服务端 |

不能仅把本地JSON存档上传到数据库。在线模式不接受客户端覆盖等级、金币、任务或战斗结果。

## 3. 技术栈与部署拓扑

| 部分 | 方案 |
|---|---|
| 游戏客户端 | Godot、GDScript |
| 服务端 | Rust，稳定工具链，依赖版本在实施时锁定 |
| 异步运行时 | Tokio |
| HTTP与WebSocket | Axum |
| 协议与配置 | Serde、JSON |
| 数据库 | PostgreSQL、SQLx、版本化迁移 |
| 日志与追踪 | tracing；指标接入方式在实现时选定 |
| 初期部署 | Docker Compose、TLS反向代理、单游戏进程与数据库 |

```text
Godot客户端
  ├── HTTPS：账号、登录、角色选择、连接凭据
  └── WSS：地图、移动、聊天、交互、战斗
          ↓
      TLS反向代理
          ↓
      Rust游戏进程
          ├── 会话/地图/聊天/个人战斗
          └── PostgreSQL连接池
```

初期不引入Redis、消息队列、Kubernetes或多机分片。1000人目标先通过单进程方案压测验证；需要多进程时再增加跨进程会话与广播机制。

## 4. 状态归属与模块边界

| 状态 | 权威归属 | 可见范围 |
|---|---|---|
| 地图实例、玩家位置、朝向、移动状态 | 地图模块 | 同实例内的可见玩家 |
| 账号、会话、角色归属 | 认证与会话模块 | 本人及受控管理接口 |
| 属性、背包、装备、任务、奖励 | 角色业务模块与数据库 | 本人 |
| 个人任务怪状态及交互资格 | 个人任务/世界业务 | 本人 |
| PVE状态、随机数、回合和结果 | 战斗模块与数据库 | 本人 |
| 公共消息、发言权限 | 聊天模块 | 已认证的公共频道订阅者 |
| 动画、相机、插值、界面状态 | 客户端 | 本地表现 |

### Rust并发模型

- 每条连接负责认证后的收发、心跳、协议校验和有界发送队列。
- 每个地图实例由一个任务顺序处理移动、进入、离开等消息，避免多个任务随意修改地图状态。
- 同角色关键业务串行化；单个角色只能有一个有效在线会话和一个活动PVE战斗。
- 战斗规则尽量实现为不依赖网络和数据库的同步逻辑，便于固定随机源测试。
- 数据库操作异步执行，地图更新循环不等待数据库或慢连接；完成结果通过消息返回相应业务所有者。
- 不以一个全局`Arc<Mutex<World>>`保护所有在线玩家，不跨`.await`长时间持有共享状态锁。
- 异步完成消息携带会话代次/状态版本，过期连接的回调不能写入新的会话状态。

模块间涉及战斗进入、切图等流程时，由明确的协调流程保证状态一致；超时或失败不得留下“地图可移动但已经进入战斗”的双重状态。

## 5. 地图、移动与个人怪物

- 服务端持有权威阻挡、传送点、出生点、怪物与任务配置。
- 将现有地图生成逻辑和配置提取为可版本化数据，客户端与服务端校验配置版本；不各自维护容易漂移的随机地图。
- 首版沿用四向、格子寻路，服务端校验目标、路线、速度和交互距离。
- 玩家移动即时在本地表现，服务端确认后校正；远端玩家使用插值。
- 人物步伐依旧按实际显示位移推进，不按收到网络包的次数推进。
- 地图更新先以10Hz为起点，采用网格可见范围和增量同步，不全服广播每个人的位置。
- 玩家互不阻挡作为首版建议；是否启用玩家碰撞另行确认，不能让拥挤导致任务入口永久堵塞。
- 任务怪属于玩家个人进度，击杀不会删除其他人的怪物，个人巡逻和交互状态不广播给全图。
- 私有怪物是否存在、其交互位置和距离由服务端判定；不能信任客户端上报“已经靠近怪物”。
- 弹出个人页面或进入战斗不暂停整个地图；个人怪物的暂停语义与现有单机表现单独适配。

当前地图仅32×32格。网格可见范围并不能自动解决1000人聚集同一区域的最坏情况；热点容量、分线和可见人数口径需要明确后单独验收。

## 6. 战斗与个人业务

建议角色战斗时留在原地图，向其他玩家显示“战斗中”，禁止移动，战斗画面和敌人仅本人可见。

服务端接收指令后完成规则校验、计算、可靠保存，再返回有序事件。客户端依次播放攻击、伤害、血条和结算，动画时长不决定服务端结果。

- 随机数、伤害、消耗和奖励由服务端产生。
- 延续当前职业规则与30回合上限，迁移时用固定随机源校验行为，不顺便更改数值体系。
- 战斗中限制装备、地图外用药等冲突操作；战斗道具消耗与角色实际库存统一结算。
- 同一回合指令不能重复生效，同一战斗奖励只能发放一次。
- 战斗断线后保留可恢复快照；具体保留时间和超时结算策略尚待确认。
- 自动战斗沿用相同指令校验，不允许绕过回合版本和指令节奏限制。

## 7. 持久化与一致性

建议逻辑表：`accounts`、`sessions`、`characters`、`inventory_items`、`quest_progress`、`battles`、`battle_commands`、`reward_grants`、`operation_receipts`、`currency_ledger`、`moderation_actions`。聊天审计是否持久化及其保留期单独确定。

- 初期可以对部分快照使用有版本的JSONB；账号归属、唯一性、奖励和幂等键必须能受数据库约束保护。
- 购买扣款和物品增加在一个事务内完成，任务推进与奖励发放同理。
- 有经济影响的战斗回合应原子保存战斗修订、资源变化、操作回执；最终回合一并提交结果和奖励。
- 数据库事务成功后才确认成功并推送权威结果。提交成功但响应丢失时，通过操作回执找回结果。
- 服务端重启从持久化状态恢复，不依赖内存中的“已经发过奖励”标志。
- 位置不逐帧入库，建议每10～30秒以及切图、正常退出时保存；异常退出可能回退少量位置。
- 装备、货币、道具、任务与战斗关键状态不能套用位置的宽松保存策略。
- 优雅停机停止接收新会话，完成或中止在途事务，保存合法位置，客户端收到维护提示；强制退出仍依靠已提交数据恢复。

离线存档与线上角色隔离。不能把可修改的本地JSON视为可信线上资产；如需导入，另行设计受控、一次性迁移方案。

## 8. 公共聊天与公网安全

- 公共频道跨地图广播，发送者ID、名称和时间取自服务端。
- 建议单条最多128个Unicode字符，另设UTF-8字节上限；初始限速可设每2秒1条、短时突发3条，全部配置化。
- 账号限速之外增加全局保护、连接消息速率限制、禁言与封禁检查。
- 内容按纯文本展示，避免Godot富文本标记注入；不记录或广播密码、令牌等敏感字段。
- 可靠业务事件不能任意丢弃；可替代的旧位置更新可以合并。聊天队列持续拥塞时应提示或断开慢连接，不无限占用内存。
- 公网只暴露TLS入口；数据库、指标和管理接口放在私网或受控网络。
- 密码使用Argon2id等成熟密码哈希方案；哈希计算放入有并发上限的阻塞任务，不阻塞异步执行器。
- 登录、注册、连接建立、消息大小和操作频率分别限额；IP限制不能取代账号限制，也要考虑同一出口的正常玩家。
- 密钥通过环境或受控配置注入，不提交仓库；日志脱敏，会话支持撤销与过期。
- 反向代理配置WebSocket升级、连接超时及转发来源信任边界；基础防护不等于具备抗大规模DDoS能力。
