# 实施路线

设计修订：2026-10-15。客户端目录迁移、服务器地址记忆、Rust基础服务、PostgreSQL账号认证及线上角色创建/查询已实现；M1中的WSS票据及角色执行器仍待推进，不能视为整个M1完成。

产品边界和D01～D08决策以[设计入口](README.md)为准，技术设计见[architecture.md](architecture.md)，接口见[protocol.md](protocol.md)，具体测试与容量验收集中在[tests/online_test_plan.md](../tests/online_test_plan.md)。

## 1. 执行原则

先完成含账号、双客户端互见、一次战斗、事务回执和重启恢复的最小完整流程，再扩展地图同步规模及全部玩法。不将事务一致性推迟到所有界面和聊天完成之后，也不把压测和监控全部留到公网发布时。

首版最终交付仍包含多人地图、公共聊天、个人任务和独立PVE。阶段交付不是缩减首版功能；暂不引入微服务或多机分片；已确认首版不自动分线、不按人数隐藏可见玩家。D01～D06及D08昵称唯一性已获用户确认，按确定规则推进；尚待确认的部署/运营项只保留相应发布关口。

已有目录迁移作为独立工作保留，不重做、不与后续业务重写混为一次变更。每阶段只改相关范围，保留其他工作区改动；实际Git提交按明确要求单独执行，不以文档中的“阶段”隐含提交授权。

## 3. 后续阶段

### M0：规则清点与契约冻结

前置：保留已完成迁移，确认设计文件对应当前目录。

工作：清点`client/scripts/`所有写角色/资源的入口；明确GameService与离线/在线适配；导出地图地形和树木阻挡、出生点、传送点、怪物、任务、物品与战斗规则。建立实际需要的`shared/protocol`、`shared/data`和`shared/fixtures`，定义ID、版本、幂等、快照分块、昵称统一校验/name_key规范化及固定随机取值样例。

出口：每个现有可改变玩法状态的入口有明确线上契约或本地显示归属；个人怪物、任务前置、背包容量和战败回城不遗漏。完整schema只冻结本阶段将实现的消息，后续新增受版本控制，不以空接口声称功能可用。

### M1：业务接口、服务骨架与账号角色

已确认前置：D03为每账号一个角色、一个有效游戏会话，同登录会话可重连接管、不同登录会话拒绝第二次上线；D05保留隔离的离线/在线双入口；D08线上角色昵称全服唯一、不允许重名，不再等待这些选择。

工作：基于现有Rust/Axum/Tokio工程核对并补齐配置、健康/就绪检查、结构化日志和基本指标；建立PostgreSQL迁移、账号密码、令牌轮换/撤销、角色创建和WSS单次票据认证。实现独立于连接的CharacterActor、所有权注册、在途写入屏障、回执基础能力和GameService适配。在线页面不得再直接写本地资产。

出口：认证/归属隔离有效，同登录会话重连接管不会重建角色业务；无权限连接不能读世界。基础去重、会话撤销和数据库恢复路径可验证。创建角色必须实现账号级回执、UNIQUE(account_id)、UNIQUE(name_key)及NAME_TAKEN/CHARACTER_LIMIT_REACHED错误；并发抢名仅一个成功，原成功操作重试返回原角色，不自动加后缀。服务端仅有占位目录不算完成M1。

### M2：最小联机完整流程

已确认前置：D01按全服1000人混合游玩、单实例热点另测；D02不自动分线/按人数隐藏；D04断线冻结60秒、在线5分钟无有效指令按主动逃跑结束，保留消耗且不发胜利奖励；D06玩家互不阻挡，战斗原地标记，个人页面仅暂停本人输入和个人怪物。先完成双客户端流程，不以此宣称1000人容量。

工作：两个真实客户端进入同实例，具备最小权威移动、实体进出、完整快照/增量衔接、单个NPC、一个个人怪物、一种道具的购买/消耗和独立PVE。实现一场战斗开始、每个有效回合、最终奖励及回执持久化；初期即覆盖重连、关键位置保存、事务未知和服务重启。

出口：完成“进入→互见→接任务→挑战→结算→断线/重启→恢复”流程，个人怪物不影响其他人；重复请求不重复扣款/发奖，旧连接结果不会丢失或覆盖新快照。开始小规模混合负载，验证监控与资源预算确实可观测。

### M3：地图同步、公共聊天与中等规模验证

前置：M2事务和恢复不变量成立；冻结具体混合负载与单实例热点口径，不自动套用分线。

工作：补齐地图同步、可见集合、分块限额、实体重新进入、序号、插值、慢连接保护和集中重连；实现跨地图公共聊天、短期去重、纯文本展示、个人与全局公平限流、有限历史及禁言。优化地图入口寻路限流、漏tick行为、位置合并、数据库队列和客户端每帧处理预算。

出口：在记录的环境上完成50/200/500人阶梯负载并明确瓶颈，执行热点和慢客户端场景；没有越过产品决策的人数裁剪。未达到阶梯目标时保留事实与限制，不跳过失败进入容量宣传。

### M4：完整现有玩法与客户端体验

前置：最小流程稳定，角色业务入口已全部清点。

工作：接入两张地图、三只山狼任务、领奖和遗迹妖王，补齐三职业、完整背包、NPC恢复、调息、签名、门派身份和切图/战败回城。完善战斗有序事件、自动操作节奏、规则版本恢复与真实渲染；保持原数值，不自增重复任务/怪物刷新。

出口：线上走通完整任务链；在线/离线隔离、各业务前置与60格/99堆叠规则正确，旧规则活动战斗可恢复，动画不影响结算。目标客户端渲染和长时内存观察不能由无渲染机器人代替。

### M5：公网、故障恢复与目标容量验收

前置：D07部署预算/地域/RPO/RTO，D08中仍待确认的聊天历史/审计保留、账号管理及其他发布事项确认；素材来源与授权完成核验。

工作：TLS与代理、私网数据库/管理、备份和必要的WAL恢复策略、优雅停机、迁移兼容与单写发布。在确定机器/网络/数据库条件下验证约定1000人混合负载、单实例热点、集中重连及资源泄漏。完成数据库故障、磁盘/备份恢复和旧规则发布演练。

出口：按测试计划记录实际容量、延迟分位数、错误率、客户端帧耗时和恢复表现；分别说明全服在线、同实例互见和客户端显示范围。达不到目标时调整预算/方案并重新验收，不用1000空闲连接或隐藏玩家替代。

## 4. 技术风险与对应实现关口

| 风险 | 设计约束 | 实施关口 |
|---|---|---|
| 并发创建重名/多角色，或成功重试被误判重名 | 全服name_key唯一、一账号一角色、账号级回执优先于新操作查重 | M1 |
| 重连丢弃旧事务回调，数据库与新角色缓存不一致 | CharacterActor不随连接销毁；查清在途结果后同步 | M1～M2 |
| 旧operation_id先遇到版本冲突，客户端重复购买 | 查回执先于新操作业务版本校验；数据库唯一键兜底 | M1～M2 |
| 战斗/切图与地图移动双重状态、旧位置覆盖回城 | 准备冻结、原子稳定状态、幂等投递、world_epoch条件保存 | M2 |
| 半份快照叠加实时事件，产生残影或遗漏 | 不可变快照边界、临时安装、订阅级序号与生命周期 | M2～M3 |
| 战斗重试重新随机、更新规则破坏旧战斗 | 固定规则快照、随机状态同事务保存、旧版本恢复 | M2～M4 |
| 只按battle_id去重却能反复刷同一私人怪物 | 个人遭遇预约/消费与奖励来源唯一约束 | M2～M4 |
| 同步/寻路/数据库等待无限堆积 | 全链路消息数/字节/滞留限额、公平队列和有界tick处理 | M1～M3 |
| 客户端界面暂停导致网络停轮询、双重结算 | 独立NetworkClient、GameService与只读线上快照 | M1～M4 |
| 全图热点广播和全局聊天放大 | 单独预算及热点验收，不擅自分线/隐藏 | M3～M5 |
| “恢复不丢失”混淆进程崩溃与历史备份 | 按故障类型验收，单独确认RPO/RTO与备份策略 | M5 |

## 5. 决策与变更纪律

D01～D08状态以设计入口为准；本轮已同步用户确认的D01～D06及D08昵称唯一性。M1、M2不再因这些选择阻塞；M5仍等待D07及D08运营项。产品期限60秒/5分钟不得当作性能调优参数擅自更改，其他未定技术限额通过配置与验收冻结。后续用户选择变化时同步受影响章节和测试条件，不悄悄改变已确认规则。

需求变化、规则配置和协议变化分别版本化。实现中发现无法满足“同地图互见”或当前单次任务规则时，先报告具体瓶颈及选择，不通过自动分线、复活怪物或改奖励公式掩盖。每阶段完成情况以实现与测试记录为证据，不以设计段落存在为完成标准。
